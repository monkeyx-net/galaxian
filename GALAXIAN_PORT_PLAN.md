# Galaxian native port: plan

A C11 / SDL2 port of Galaxian (Namco, 1979; MAME `galaxian`, Namco set 1
with the Midway program ROMs) that plays like the arcade game, for
PortMaster handhelds (aarch64), desktops (x86_64 Linux, Windows, macOS) and
the web. It is converted the same way as the sibling Defender port
(`../defender`): emulate the board, check the emulator against MAME 0.289,
extract the assets once, then rewrite the game in C, checked frame by
frame against the emulated board.

The repository started on 2026-10-22 as a copy of Defender's skeleton
(platform layer, loaders, framebuffer, enhanced graphics, packaging, CI,
MAME harness), itself from the Joust and Robotron ports. The hardware
(Z80 board, video, discrete sound) is new.

## 1. Decisions (2026-10-22)

1. **The ROM set is read once** (as Defender's decision 1). The binary
   never embeds ROM-derived data; it loads it at run time from an `assets/`
   folder that `galaxian --extract <galaxian.zip>` writes from the player's
   own ROM set (the PortMaster launcher runs it on the first start). The
   repo, CI and releases carry no ROM-derived data: not tiles, sprites, the
   font, the palette or tables; the extractor's tables name ROM addresses
   only. Sound is generated by a model of the discrete circuit, so nothing
   is extracted for it. Until the game is in C, the emulated board runs the
   ROM's code and reads the ROM set.
2. **MAME is the reference.** Behaviour is established by probing the ROM
   in MAME 0.289 and checked by CTest against the port. Probes are Lua and
   only dump; C or CMake compares. Emulation is written from the hardware's
   behaviour, not from MAME's source.
3. **Shared code is copied, not linked**, from `../defender/src` (renamed
   defender → galaxian): `platform/`, `gfx/` (bar `williams.c`),
   `assets/` (with a new `rom.c`), `packaging/`, `web/`, CI, the MAME CMake
   and Lua harness. Fixes found here that apply there are listed in
   section 5, to carry across once agreed.
4. **Controls:** one control panel (the players take turns), as the upright
   cabinet: left/right and fire. Pad: stick or D-pad left/right, A or B
   fire; every pad drives the panel. Select = coin, Start = 1P, L1+Start =
   2P, Select+L1 = graphics presets, hold Select+Start 1 s = exit.
   Keyboard: arrows left/right, Space/Ctrl fire, 5 coin, 1/Enter and 2
   start, F3 presets, F4 glow, F5 scanlines, Esc exit. The DIP switches
   (coinage, bonus life, lives) come from a settings file (`galaxian.cfg`)
   with MAME's defaults.
5. **Enhanced graphics** as in the Defender port (FILTER and HD presets,
   glow, scanlines), cosmetic only, classic by default. The screen is
   portrait (224x256, the monitor turned 90 degrees): integer scaling where
   it fills the screen, else fitted (640x480 handhelds: 1.875x, sharp
   bilinear, pillarboxed); the scanlines run down the screen.
6. **The game in C.** The game logic is rewritten in C (`src/sim/`), from
   the ROM's behaviour (traces, probes, the disassembly MAME writes to
   `build/re`, never committed), routine by routine, each mirroring the
   ROM's arithmetic. The emulated board (`src/emu/`, checked against MAME
   by `mame_emu`) stays as the reference the C game is compared with.
7. **High-score saving** (a port feature: the arcade forgets its high
   score at power-off): `galaxian.hiscore` in the save folder.

## 2. Hardware

Confirmed so far (MAME 0.289's view, by probe):
- ROM set (`rom_load`, `mame_rom_map`): program `galmidw.u` 745e2d61
  ($0000), `.v` 9c999a40 ($0800), `.w` b5894925 ($1000), `.y` 6b3ca10b
  ($1800), `7l` 1b933207 ($2000); graphics `1h.bin` 39fb43a4 and `1k.bin`
  7e3f56a2 (MAME region `:gfx1`, 4 KB: 1h then 1k); palette PROM `6l.bpr`
  c3ac9467 (`:proms`, 32 bytes). MAME's `:maincpu` region is 16 KB.
- CPU: Z80 at 3.072 MHz. Screen: 768x224 in MAME (its pixel clock is
  18.432 MHz, three times the board's 6.144 MHz, so 256 board pixels a
  line), 1152 clocks a line (384 board pixels), 264 lines, visible lines
  16-239, 60.606 Hz; turned 90 degrees.
- Inputs (MAME's ports; active high):
  - IN0 ($6000): coin 1 01, coin 2 02, P1 left 04, P1 right 08, P1 fire
    10, cabinet 20 (cocktail), service mode 40, service 1 80.
  - IN1 ($6800): 1P start 01, 2P start 02, P2 left 04, P2 right 08, P2
    fire 10, coinage C0 (00 1C/1C default, 40 2C/1C, 80 1C/2C, C0 free).
  - IN2 ($7000, the DIP switches): bonus life 03 (00 7000 default, 01
    10000, 02 12000, 03 20000), lives 04 (set: 3, the default; clear: 2),
    unused 08.

Confirmed in E1 (`mame_emu`: the Z80 cycle for cycle over 100 frames of
play; RAM, tile and object RAM, latches and every pixel at 14 frames):
- Memory map (probe): $0000-$3FFF ROM ($2800-$3FFF read 0), RAM
  $4000-$43FF mirrored once to $47FF, $4800-$4FFF reads $FF, tile RAM
  $5000-$53FF mirrored to $57FF, object RAM $5800-$58FF mirrored to $5FFF,
  IN0 / IN1 / IN2 at $6000 / $6800 / $7000 (each over 2 KB), $7800 reads
  $FF (the watchdog), $8000-$FFFF reads $FF. Latches decode A0-A2 over
  their 2 KB and keep bit 0.
- The Z80 at power-on (MAME's): AF $0040, IX = IY = $FFFF, the others 0,
  SP 0 (the game sets SP to $4400 itself; its stack never goes below
  $43DA).
- Frames: 264 lines of 192 cycles (50688), line 240 (vertical blank)
  starting at cycle 50688 k. The NMI flip-flop is set there if $7001 bit 0
  is set (writing 0 clears it); MAME raises the NMI a cycle before the
  line starts: an instruction ending at or after cycle 50688 k - 1 is
  followed by it (11 cycles: PC pushed at T 5 and 8). The handler is at
  $0066 (it pushes AF BC DE HL IX IY, then writes 0 to $7001).
- Writes take effect at their machine cycle's start (LD (nn),A at T 10).
  MAME draws a line lazily: a write to the tile or object RAM or a video
  latch first draws every line that has started, so a line shows the video
  as it was when the line began. The game rewrites sprites during the
  frame (the player's ship), so this matters.
- Tiles: tile RAM row r is board lines 8r-8r+7 (screen column 239 - line),
  column c pixels 8c-8c+7 along the line (down the screen). Object RAM 2c
  scrolls column c along the line ((line + scroll) & 255 picks the tile
  row), 2c+1 is its colour (bits 0-2). A tile is 8 bytes in each of 1h
  (the pixel's high bit) and 1k (its low bit), a byte per line, bit 7 the
  first pixel along it. Pixel 0 is transparent (the stars show).
- Sprites ($5840-$585F, 4 bytes: y, code bits 0-5 with flip-x 40 and
  flip-y 80, colour, x): 16x16, the four tiles 4 code to 4 code + 3 (+1
  the next 8 pixels along the line, +2 the next 8 lines). Sprite i covers
  lines 240 - y to 255 - y, one line later for sprites 0-2, pixels x + 1
  to x + 16. The port draws sprite 0 over the others and shells over
  sprites (not yet seen overlapping in a capture).
- Shells ($5860-$587F, 4 bytes, bytes 1 and 3 used): entry i is drawn on
  line 255 - byte 1 (one line later for entries 0-2), 4 pixels from 251 -
  byte 3; entries 0-6 white ($FFFFFF), 7 (the missile) yellow ($FFFF00).
- Palette (6l): red bits 0-2 and green bits 3-5 weigh 29, 62, 133; blue
  bits 6-7 weigh 69, 148 (MAME's values). Colour c of a tile or sprite
  uses entries 4c-4c+3.
- Stars: a 17-bit shift register (sr >> 1 | ((sr >> 12) ^ ~sr) & 1 <<
  16, from 0), two steps a board pixel, 512 a line. A step is a star when
  (sr & $1FE01) == $1FE00, colour (~sr >> 3) & $3F: red bits 5-4, green
  3-2, blue 1-0, each 0, $D6, $C2, $FF. The first step of a pixel is MAME's
  first third of it, the second its other two. Shown where bit 0 of the
  line differs from bit 3 of the pixel, and where the tiles and sprites
  leave black. The generator is held clear while $7004 is 0; set, it runs
  from that moment: line 0's first step is then 131071 - (line x 512 + 6
  x the cycles into the line) (mod 131071), and at each vertical blank the
  origin moves back one step (the stars scroll).
- Inputs a MAME probe sets in its frame callback reach the game at the
  start of the next frame.

- The watchdog (probe): 8 vertical blanks without a read of $7800 reset
  the board (the CPU and the latches; RAM keeps its contents).

To confirm: the flip latches ($7006/$7007, the cocktail cabinet).

### 2.1 Sound (E2, measured from MAME's output)

Each source was recorded with `-wavwrite` while the CPU idled (the probe
replaces the program with `LD A,($7800)` / `JR` to feed the watchdog) and a
Lua script set one latch at a time; analysed with spectra, zero-crossing
tracks and the jumps of the high-passed output. `emu/sound.c` models each
from these measurements (generated: nothing from the ROM set). A sample at
48 kHz is exactly 64 CPU cycles: 792 a frame.
- The output passes a one-pole high-pass, 0.99792 a sample (10 ms); every
  level below is in MAME's output units before it.
- Tone ($7800, $6806 VOL1, $6807 VOL2): an 8-bit counter clocked at
  1.536 MHz, loaded with the pitch on overflow, steps a 4-bit counter
  (1.536 MHz / (256 - pitch): 750 Hz at 0 with the volume bits off,
  $FF silent). A DAC sums q0, q1^q2 and (q1&q2)^q3 with weights by volume:
  off 1900, 2849, 0; VOL1 1388, 6665, 0; VOL2 1526, 2288, 3356 (the third
  input makes a 16-step period, an octave down); both 1177, 5651, 2591.
  The level is the counter's at each sample (so $FC-$FF are silent and
  $FD aliases to 16 kHz, as MAME's). The game plays the coin sound (pitch
  $04 to $80, 4 a frame), the tunes and the aliens' sounds with it.
- Swarm ($6800-$6802 FS1-FS3, the LFO $6004-$6007 = bits 0-3): three
  555s, 237.5 -> 124, 332 -> 169.5, 483.5 -> 238.5 Hz, the frequency falling
  linearly over one LFO period then jumping back. Their low half is fixed
  (156, 109.5, 73.1 samples), the high half the rest. The LFO period by its
  value 0-15: 0.164 0.173 0.184 0.194 0.212 0.226 0.245 0.264 0.324 0.359
  0.407 0.463 0.573 0.687 0.886 1.194 s; it changes at once when the bits
  do. Each square is 4560 peak to peak, through a 14.5-sample low-pass;
  the volume bits load the mixer: x1, 0.827, 0.933, 0.714 (VOL1, VOL2,
  both). A latch at 0 holds its square low. The game turns FS1-3 on at a
  game's start and steps the LFO value down by one every 256 frames.
- Hit ($6803): the noise generator steps at 8 kHz (every second line; a
  17-bit shift register in the model). Its bit swings +-52000 through a
  147-sample low-pass and a resonant high-pass (s^2 + s/2.3) / (s^2 +
  s/2.4 + 1) at 152 Hz; full at once when set, fading with 0.71 s when
  cleared. The game holds it about 39 frames (an explosion).
- Fire ($6805): an oscillator whose edges come through a near
  differentiator as clicks of 10250 decaying x0.3128 a sample; its rate is
  jittered +-30% by the noise bit, rising from 2.5 kHz towards 4.6 kHz
  (0.07 s) while set and back (0.1 s) after; the clicks fade with 0.19 s
  when cleared. The game holds it 8 frames per shot.
- $6804 makes no sound (the game writes it with the aliens' tone sounds).
- Not modelled: MAME's thump at power-on as its filters charge (the
  first half second).

## 4. Tests

- `enhance` - always runs (scalers, presets, glow)
- `rom_load` - label `rom`: the set from the zip, from renamed copies in a
  folder (CRC matching), and a clean failure on an empty folder
- `mame_rom_map` - label `mame`: MAME's view of the program ROM
  ($0000-$27FF), the graphics and the PROM equal `galaxian --dump-rom`
- `z80` - always runs: every opcode's T-states (the documented counts,
  branches taken and not), the machine cycles adding up to them, where
  writes fall, known flag results (DAA, overflow and half carries, CP's
  and BIT's bits 3 and 5, the block group, 16-bit arithmetic), NMI, IM 1,
  HALT
- `mame_capture` - label `mame`: runs the scripted game in
  `src/tests/mame/script.cmake` (attract mode, coin, start, over a minute
  of play), dumping RAM, tile and object RAM and the latches with a
  snapshot at 14 frames; the static frames drawn from the dump
  (`gfx/galaxian.c`) equal MAME's snapshots (bar the stars)
- `mame_emu` - label `mame`: the board replays the script from power-on.
  MAME's instruction trace of frames 1600-1700 (`trace_probe.lua`): the
  Z80 cycle for cycle. At every captured frame RAM (bar the stack,
  $43C0-$43FF), tile and object RAM, the latches and the picture (MAME's
  224x768) are MAME's. The sound against MAME's recording of the run
  (`game.wav`, from `mame_capture`): in 1/10 s windows where MAME is not
  quiet, at least 90% within 3 dB of its level (today all of them); where
  the tone plays alone, its pitch and level (1 dB) exact.
- Later: `extract`, `sim`, `game`, `routines`, `frame` (as Defender's).
- Probes that are not tests: `ram_probe.lua`-style dumps come from
  `capture_probe.lua` (`PROBE_FRAMES`, `PROBE_POKE`); `test_emu` takes
  `DUMP_DIR` (its pictures), `OBJECT_LOG=frame` (object RAM line by line),
  `LATCH_LOG=1` and `WRITE_LOG=addr` to chase a difference.
